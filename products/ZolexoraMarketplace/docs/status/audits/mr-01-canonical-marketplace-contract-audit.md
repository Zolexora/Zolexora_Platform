# MR-01 Canonical Marketplace Contract Audit

## 1. Executive Verdict
The repository exhibits a severe architectural disconnect. While Phase 1 (MR-00) correctly established request-level storefront context resolution (`StorefrontContext`), the backend application layer (`routers` and `models`) completely ignores this context. All data models lack `storefront_id`, meaning products, orders, and users exist in a single global namespace. Furthermore, the domain models are tightly coupled to specific payment providers (Razorpay, UPI) and legacy Mahila Madel features (Coins, Reels), violating the provider-neutral, multi-storefront architecture defined in `ADR 0001` and `ADR 0008`. Frontend clients and backend schemas are manually synchronized, leading to duplicated and divergent contracts.

## 2. Repository Areas Inspected
- `services/marketplace-api/routers/` (FastAPI controllers)
- `services/marketplace-api/models/` (Pydantic and Database Document Models)
- `services/marketplace-api/storefronts/` (Storefront Context Resolution)
- `packages/shared-api/src/types.ts` (Frontend TypeScript interfaces)
- `docs/` (Architecture and Decision Records)

## 3. Current Contract Ownership Map
Currently, there is no single source of truth.
- **Backend**: Pydantic `BaseModel` classes defined in `models/documents.py` act as the de-facto schema for database documents and API definitions, but are not strictly enforced in all router responses.
- **Frontend**: `packages/shared-api/src/types.ts` manually re-declares TypeScript interfaces.
- **OpenAPI**: Generated by FastAPI but completely unused by the frontend workspace.

## 4. Backend/Frontend Mismatch Table
| Domain | Backend Field | Frontend Field | Mismatch / Risk |
|---|---|---|---|
| Products | `category: str = "Other"` | `category: ProductCategory` | Backend allows any string, TS enforces union enum. |
| Orders | `coins_discount: float` | `coins_discount: number` | Decimal-unsafe float usage in Python for monetary values. |
| Orders | `admin_note: Optional[str]` | `admin_note: string \| null` | Nullability is manually synced and fragile. |
| Core | `id: str` (UUID) | `id: string` | IDs are opaque strings; no strong typing for domain IDs. |

## 5. Duplicate-Definition Inventory
Every major domain entity is duplicated between:
- `services/marketplace-api/models/documents.py` (e.g., `ProductDoc`, `OrderDoc`, `UserDoc`)
- `packages/shared-api/src/types.ts` (e.g., `Product`, `Order`, `User`)
There is no automated generation or verification keeping these in sync.

## 6. Storefront-Context Findings
- **Resolution**: `StorefrontRegistry` correctly validates Host, `Origin`, and `X-Storefront-Key`, safely rejecting conflicts and failing closed.
- **Propagation**: The resolved `StorefrontContext` is completely unutilized by domain routers (e.g., `routers/products.py`).
- **Data Models**: `ProductDoc`, `OrderDoc`, `CartItem`, etc. all lack a `storefront_id` field. `GET /products` returns global catalog items unconditionally.
- **Isolation Risk**: CRITICAL. A Mahila Madel request can see and interact with Zolexora Shop products and users.

## 7. Authentication and Authorization Findings
- `UserRole` is restricted to `"viewer" | "seller" | "admin"`.
- Sellers are isolated by `seller_id` on products, but seller identity is not mapped to an overarching "Organization" or legal entity.
- There is no storefront tenant boundary on authentication sessions.

## 8. Provider-Coupling Findings
- **Payments**: `OrderDoc` explicitly declares `razorpay_order_id`, `razorpay_payment_id`, and `upi_transaction_ref`. The `CheckoutResponse` exposes provider-specific metadata directly.
- **Legacy Mahila Features**: Core user and order documents have `coin_balance`, `coins_used`, `coins_discount`, tightly coupling the shared marketplace backend to Mahila-specific promotional mechanics.
- **Storage**: `ProductDoc` comments and fields specifically reference `Cloudinary CDN URLs`.

## 9. ERP-Boundary Findings
- No ERP mapping fields, external identifier correlation tables, or event outbox mechanisms exist in the models. The ERP boundary is currently non-existent in the schema.

## 10. Security and Tenant-Isolation Risks
- **Severity**: CRITICAL
- Storefront spoofing via Host headers is blocked by MR-00, but because the routers don't filter queries by `storefront_id`, cross-store data leakage is immediate and unconditional.
- The use of `float` for `price` and `subtotal` risks floating-point arithmetic errors in checkout calculations.

## 11. Proposed Canonical Contract Architecture
1. **Single Source of Truth**: Pydantic models in FastAPI dictate the schema. OpenAPI JSON is generated and used by `openapi-typescript` in `packages/shared-api` to generate strictly typed frontend clients.
2. **Context Injection**: Every storefront-scoped router endpoint must depend on `StorefrontContext` and pass `storefront_id` to the service layer.
3. **Data Models**: Add `storefront_id` to all scoped entities (Products, Listings, Carts, Orders). Separate Master Product from Storefront Listing.
4. **Decimals**: Convert all monetary amounts to `decimal.Decimal` in Python and integer cents/strings in JSON transport.
5. **Provider Neutrality**: Replace `razorpay_` fields with an abstract `PaymentIntent` and provider-opaque metadata JSON payload.

## 12. Proposed Files to Create, Change, Move or Retire
- **Retire**: `packages/shared-api/src/types.ts` (replaced by generated client).
- **Change**: `models/documents.py` (split into domain-specific Pydantic schemas in `models/catalog.py`, `models/orders.py`, etc.).
- **Change**: All routers in `routers/` to enforce `storefront_id` checks.
- **Create**: OpenAPI export script `scripts/generate_openapi.py`.
- **Create**: `contracts/marketplace/` as the home for JSON Schemas and exported API definitions.

## 13. Compatibility and Migration Strategy
- No live database exists yet (per MR-00), so destructive model changes in code are perfectly safe. We will replace the entire schema layer in code before generating Alembic/Oracle migrations (Phase 4/5).

## 14. Test Strategy
- Create Pytest fixtures that inject known `StorefrontContext`.
- Add router tests that simulate requests from two different storefronts and verify that products/orders from Storefront A are invisible to Storefront B.
- Compile TypeScript against the generated OpenAPI types to catch any frontend regressions.

## 15. Ordered Implementation Batches
- **MR-01A**: Contract foundations (Abstract Base Models, standard Error envelope, Decimal types, OpenAPI generation script).
- **MR-01B**: Storefront identity (Inject `storefront_id` into scoped models and routers).
- **MR-01C**: Catalog and inventory contracts (Master Product vs Storefront Listing).
- **MR-01D**: Cart and checkout contracts.
- **MR-01E**: Orders, fulfilment, cancellation, and returns.
- **MR-01F**: Provider-neutral payment contracts (remove Razorpay coupling).
- **MR-01G**: Seller/admin contracts (Organization mapping).
- **MR-01H**: ERP boundary (Outbox/Inbox and mapping tables).
- **MR-01I**: OpenAPI/frontend synchronization (Swap `shared-api` to generated types).

## 16. Blockers and Decisions Requiring User Approval
- **Decision 1**: Confirm the transition from float/numbers to Decimal/integer-cents for all monetary values.
- **Decision 2**: Confirm the removal of legacy `coins_*` fields from the core `Order` contract, potentially abstracting them as generic "Promotions/Discounts" to maintain provider neutrality.
- **Decision 3**: Approve the batch plan to begin implementing **MR-01A** (Foundations).

## 17. MR-01F Provider-Neutral Payment Contracts

* **Canonical Payment Ownership**: `PaymentIntent` defines a provider-neutral interface relying entirely on `Money` for exact representations (amounts/refunds) without float instability.
* **Public versus Internal Fields**: The public `PaymentIntent` schema omits provider keys (`razorpay_order_id`, `razorpay_signature`). Internal metadata is encapsulated in the `InternalProviderMetadata` model, strictly separated from frontend contracts.
* **Storefront-to-Provider Selection Boundary**: `StorefrontContext` dictates the gateway configuration. Untrusted payloads cannot determine payment gateway resolution or manipulate the underlying implementation.
* **Payment State Transition Table**: Strict domain rules apply. `created` transitions to `requires_action` or `authorized`. `captured` transitions to `refunded` or `partially_refunded`. Unauthorized skips and reverse-state transitions are blocked.
* **Legacy Razorpay Compatibility Plan**: `LegacyRazorpayVerifyRequest` is retained for backwards compatibility, allowing existing cart endpoints (to be migrated in MR-01D) to map `razorpay_order_id` back to the new domain models gracefully.
* **Legacy Coins/Loyalty Migration Boundary**: `coins_*` fields in `OrderDoc` have been preserved but explicitly marked with JSON Schema `"deprecated": True`.
* **Security Restrictions**: `InternalProviderMetadata` is never serialized over the API wire, ensuring webhook secrets or raw payloads never reach clients.
* **Deferred MR-01D Work**: The actual `routers/cart.py` and checkout endpoints have not yet been migrated to use `PaymentIntent`. This remains safely deferred to MR-01D.
